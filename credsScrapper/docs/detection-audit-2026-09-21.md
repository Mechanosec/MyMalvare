# Аудит якості детекції, 2026-09-21

## Межі перевірки

Бази відкриті через SQLite `mode=ro`. Значення секретів не виводилися,
мережевих перевірок ключів не виконувалося. Дані й код застосунку не змінено.
Перевірено агрегати всіх типів, структурні ознаки вибраних типів і потоком
усі generic_high_entropy записи, порціями по 2 000. Це не ручна перевірка
кожного вихідного файлу і не встановлення чинності знайдених ключів.

Знайдено дві бази. Подальші числа стосуються `apps/api/prisma/dev.db`:
саме вона містить запис зі скриншота для `workspaces/daytona/.env.example`.
У `apps/api/dev.db` такого запису немає. Конфігурація API містить
`DATABASE_URL=file:./dev.db`; відкритого процесом дескриптора бази під час
перевірки не знайдено, тому активний runtime окремо не підтверджено.

## Відтворені причини

1. **Facebook/Twitter знаходяться всередині довшого blob.**
   `patterns.ts` не перевіряє межі токена. Поточне очищення в `engine.ts`
   прибирає data URI й певні багаторядкові MIME-блоки, але не довільне
   JSON-поле з base64-зображенням. Синтетичне поле `image/png` дає
   Facebook/Twitter-знахідку. Twitter regex обрізає збіг на 65 символах.
   Це доводить помилку механізму, але не встановлює точний відсоток
   хибних записів у базі без повторного читання джерел.
2. **Один blob потрапляє у два типи.** Той самий синтетичний приклад дає
   ще й generic_high_entropy. Перевірка overlap у `engine.ts` перевіряє
   початок entropy-токена, а не перетин двох повних інтервалів: токен,
   що починається раніше за специфічний збіг, проходить.
3. **`.env.example` не виключається.** `isExcludedPath` повертає false для
   шляху зі скриншота. Загальне виключення example-файлів знизить шум,
   але приховає й справжній ключ, випадково записаний у шаблон. Кращий
   базовий варіант — відсіювати неповні credentials та явні заглушки
   за вмістом, а не вважати кожен example-файл безпечним.
4. **GCP приймає заглушку за credential.** Досить рядкових private_key
   та client_email, їх вміст не перевіряється. Якщо JSON не вдалося
   витягнути, зберігається сам маркер service_account. Додатково GCP
   повністю звільнений від placeholder-фільтра. Синтетичний JSON із
   private_key-заглушкою відтворює проблему зі скриншота.
5. **AWS-пара не є одиницею збереження.** Синтетичні access ID і secret
   в одному тексті породжують два IFinding з окремими рядковими значеннями.
   `find-paired-aws-secret.ts` вибирає перший secret у репозиторії, без
   прив'язки до access ID, файла чи коміту. Масові перевірки admin/user
   повторюють цю логіку через `items.find`. При кількох credentials
   можливе неправильне поєднання. Самої наявної бази недостатньо, щоб
   відновити відсутні private-частини 38 інших ID.
6. **Generic-правило не вимагає ознак credential.** Високої ентропії,
   довжини й цифр досить; синтетичне поле checksum стає знахідкою.
   Не можна просто вимагати поточний context: спочатку потрібно
   виправити розпізнавання присвоєнь, зокрема JSON-ключів у лапках.
7. **PEM-детектор зберігає лише заголовок.** Поточні regex приватних
   ключів не витягають повний блок. Це окрема проблема повноти,
   аналогічна збереженню одного фрагмента GCP/AWS.

Наявність у базі записів, які вже відсіює поточний код, не доводить нову
регресію: це можуть бути результати старих сканів. Зміна детектора сама
по собі історичні знахідки не очищує.

## Конкретний порядок виправлень

1. Регресійні тести на синтетичних даних: вкладений base64, обрізаний
   Twitter-збіг, перекриття інтервалів, GCP-заглушка/повний ключ,
   JSON-присвоєння, одна й кілька AWS-пар, неповна й неоднозначна пара.
2. У наявному domain detection додати межі social-токенів, виправити
   overlap і перевірку повноти GCP. Для example-файлів зберегти
   можливість знаходити повні credentials, відсіюючи явні заглушки.
3. Збирати AWS у JSON `{"access":"...","private":"..."}` тільки за
   однозначного локального зв'язку в одному credential-блоці та версії
   файла. Не з'єднувати довільні значення з репозиторію, різних профілів,
   різних комітів або старої/нової сторони diff. Неповні знахідки
   залишати явно неповними; формат узгодити зі споживачами збережених
   значень. Окремо врахувати session token для тимчасових credentials.
4. Наступною ітерацією звузити generic-правило на основі контексту та
   дослідити JWT, PEM і підозрілі Twilio-записи. Не видаляти категорії
   цілком за одним евристичним показником.
5. Для історичних даних спочатку сформувати dry-run з ID й причинами,
   без секретів. Відсутні AWS-частини шукати повторним пасивним читанням
   авторизованих джерел. Масове видалення/перезапис бази — окрема дія
   після перегляду dry-run і резервної копії.

## Виконані перевірки

- Read-only SQL-агрегати обох баз; структурні лічильники вибраних типів.
- Повний потоковий прохід generic_high_entropy: 1 609 пакетів.
- Синтетичний виклик реального scanText та isExcludedPath успішно
  відтворив перелічені Facebook/Twitter, GCP, AWS, checksum та example-проблеми.
- Перші два запускання через ts-node не стартували через налаштування
  TypeScript 6 (moduleResolution/rootDir). Діагностичний запуск виконано
  через встановлений TypeScript transpileModule без зміни конфігурації.
- Тести всього застосунку та build не запускалися: код не змінювався.
- Реальні ключі не перевірялися через API провайдерів; бази не очищалися.

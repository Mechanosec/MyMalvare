# Глобальна зупинка сканувань

Дата: 2026-09-22
Статус: письмовий дизайн на перегляді користувача.

## Мета та погоджений обсяг

Коли адміністратор натискає **Stop all scans**, система припиняє всю незавершену роботу сканера: поточні й попередні запуски, активні задачі та задачі в черзі. Це охоплює масові `scan`, окремі `scan-repo`, повторні `rescan-service`, фазові HEAD і HISTORY та незавершені фази, які могли б відновитися після рестарту. Зупинка глобальна й не залежить від відкритого job у браузері або `parentJobId`.

Уже завершені результати, findings, кандидати, checkpoints та дані репозиторіїв не видаляються. Після завершення Stop користувач може явно запустити нове сканування. Stop не виконує live key testing і не змінює дозволи репозиторіїв.

Discovery наповнює список кандидатів, але не сканує репозиторії. Глобальний Stop сканера не зупиняє discovery; його наявна адресна зупинка лишається доступною. Нові кандидати від discovery не запускають сканування самостійно.

## Підстава в поточному коді

Поточний `StopJobUseCase` встановлює прапорець одного job через `JobQueuePort.requestStop()`. Control та фазові workers перевіряють прапорці кожні 500 мс. AbortSignal уже проходить через Piscina до worker, а Git adapter підтримує скасування активних Git-процесів. Потрібно виправити охоплення та життєвий цикл зупинки, використовуючи наявний механізм.

Виявлені розриви:

- reconciliation створює HISTORY без батьківського job;
- фаза в SQLite не зберігає контекст глобальної зупинки;
- queued фаза може почати роботу до першого таймерного stop-check;
- HEAD може створити HISTORY під час зупинки;
- скасований HEAD записується як FAILED у `ScannedRepo`, після чого `requeueFailed()` може відновити його;
- control job повідомляє про завершення HEAD та подальший HISTORY навіть після Stop;
- dashboard рахує `Scanning` за `ScannedRepo.IN_PROGRESS`, що не охоплює фоновий HISTORY.

Це висновки з читання коду, не поведінкова перевірка реалізації.

## Обрана архітектура

Використовується спільне **покоління сканування** (`epoch`) у Redis. Це номер дозволеного покоління роботи, а не ID окремого scan. Кожен scan job і кожна запланована фаза мають незмінне `scanEpoch`; дочірні задачі успадковують його. Після Stop старе покоління стає недійсним.

Глобальний стан має три значення:

| Стан | Значення |
|---|---|
| `ready` | Система приймає явні запуски; робота може бути активною або відсутньою. |
| `stopping` | Старе покоління закрито; виконується скасування та завершення обробки. Нові запуски тимчасово не приймаються. |
| `stopped` | Скасована робота вже не виконує сканування; явний новий запуск дозволений. |

Наприклад, jobs покоління `7` виконуються. Stop атомарно встановлює покоління `8` і стан `stopping`. Уся незавершена робота з `scanEpoch < 8` підлягає скасуванню. Після завершення активної роботи й узгодження persisted станів система переходить у `stopped`. Новий явний Start використовує покоління `8` і переводить стан у `ready`.

`parentJobId` може залишатися для наявної адресної зупинки та діагностики. Глобальний Stop від нього не залежить.

## Redis: атомарність і довговічність

Глобальний запис містить поточний `epoch`, стан `ready | stopping | stopped`, покоління останньої операції Stop, час запиту Stop та час його завершення. Запис не має TTL: добовий строк життя поточних індивідуальних stop flags непридатний для глобального бар’єра.

Redis adapter забезпечує атомарні переходи через підтримувані Redis операції або Lua:

- Stop із `ready`: збільшити epoch та встановити `stopping`;
- повторний Stop у `stopping`: повернути ту саму операцію;
- повторний Stop у `stopped`, якщо нової роботи не приймали: повернути завершену операцію;
- явний Start із `stopped`: перевести в `ready` та видати поточний epoch;
- Start у `stopping`: відхилити;
- завершити Stop: перевести в `stopped` тільки якщо epoch і операція досі відповідають перевіреному Stop.

Не передбачається спільної транзакції Redis, BullMQ та SQLite. Коректність забезпечують незмінне покоління, перевірки перед виконанням і повторюване узгодження станів.

### Межа одночасного Start і Stop

Root job отримує epoch атомарно при прийнятті запуску. Прийняття перед Stop означає старе покоління, навіть якщо `queue.add()` завершиться пізніше. Прийняття під час `stopping` відхиляється. Прийняття після завершеного Stop створює нове дозволене покоління роботи.

Пізній `queue.add()` зі старим epoch може створити технічний запис BullMQ, але цей запис уже не має права запускати сканування й завершується шляхом скасування. Після отримання epoch job ніколи не перечитує поточне покоління, щоб «оновити» себе або дітей.

## Черги та виконання

Бар’єр охоплює `scan`, `scan-repo`, `rescan-service` в `scanner-jobs`, усі HEAD jobs у `scanner-head` та всі HISTORY jobs у `scanner-history`. `discover` у `scanner-jobs` не бере участі в глобальному scan epoch.

### Queued jobs

До будь-якого claim фази, створення scan state, cache acquire або запуску scan worker перевіряється покоління. Недійсний job не запускає Git, сканування файлів або історії; отримує прикладний результат `stopped`; скасовує відповідний незавершений persisted стан з урахуванням epoch; не створює дочірніх jobs; не збільшує retry як помилка.

Обробка queued cancellation не повинна чекати завершення сканування кожного попереднього репозиторію. Технічні записи BullMQ можуть короткочасно лишатися для bookkeeping, але вже не є дозволеною чергою сканування. Глобальне видалення черг або даних не використовується як механізм Stop.

### Active jobs

Активні processors перевіряють глобальний бар’єр поряд із наявними індивідуальними stop flags. При закритті їхнього покоління викликається наявний AbortSignal. Перевірки потрібні перед початком роботи, під час виконання, перед claim наступного репозиторію, після HEAD перед HISTORY, між HEAD і HISTORY у `rescan-service` та перед створенням дочірньої задачі.

Таймер 500 мс означає частоту перевірки бар’єра, а не гарантію завершення очистки за 500 мс. Сканер припиняє отримувати й аналізувати нові дані; уже отримані findings можуть бути доправлені та збережені. Worker штатно звільняє lease, Git-процеси й канали повідомлень. Скасування не реалізується простим від’єднанням зовнішнього promise: фактична робота також припиняється.

## Persisted фази та репозиторії

`ScanPhase` отримує `scanEpoch`. Стан поточної спроби `ScannedRepo` також має покоління, щоб Stop не змінив новішу спробу. Покоління передається через application contracts і зберігається адаптером SQLite. Domain/application не залежать від Redis або BullMQ. Планування, claim та кінцеві записи використовують очікуване покоління; старий worker не може переписати стан новішої спроби. Для фаз додатково зберігається перевірка цільової ревізії.

### Cancellation

Фазовий `CANCELLED` лишається окремим від `FAILED`. Для `ScannedRepo` додається окремий стан скасованої спроби. Cancelled HEAD не позначається успішно завершеним, не збільшує `retryCount`, не потрапляє в `requeueFailed()` або stale IN_PROGRESS recovery та зберігає попередні успішні checkpoints. Якщо HEAD уже завершився, а HISTORY скасовано, успішний HEAD не переписується: фазові стани показують часткове покриття.

Справжні попередні failures зберігаються. Наявність глобального Stop не перетворює довільну помилку на cancellation.

### Reconciliation

Reconciliation читає persisted epoch і не присвоює поточний epoch старим pending фазам. Фаза старого покоління переходить у CANCELLED, якщо вона незавершена, не відновлюється для сканування та не обходить бар’єр при гонці між читанням стану та enqueue. Скасована фаза може бути запланована знову тільки як частина нового явного запуску.

Новий масовий Start зберігає звичайну семантику черги кандидатів; він не означає автоматичне повторення всіх скасованих репозиторіїв. Для повторного сканування такого репозиторію використовується наявний явний запуск репозиторію або сервісу. Список ще не взятих кандидатів зберігається.

## Координація завершення Stop

HTTP-запит встановлює бар’єр та повертає стан операції. Відключення браузера не перериває Stop. У worker lifecycle працює повторювана процедура завершення:

1. Застосувати скасування до старих незавершених queued jobs і persisted фаз.
2. Дочекатися припинення активних scan processors старого покоління.
3. Повторно узгодити persisted стани, щоб охопити записи, створені на межі зупинки.
4. Підтвердити відсутність активного сканування старого покоління та дозволених старих queued задач.
5. Атомарно завершити ту саму операцію Stop.

Це ідемпотентне узгодження, а не нова система планування. Воно продовжується після рестарту worker. Декілька процесів можуть безпечно повторити перевірку; лише умовний Redis-перехід завершує потрібну операцію.

«Зупинено» не показується, поки старий active processor ще сканує, записує результати або звільняє ресурси. Коротка поява processor, який тільки фіксує cancellation пізнього старого queued job, не означає відновлення сканування.

## Гонки та кінцеві результати

### HEAD завершився одночасно зі Stop

Перед HISTORY повторно перевіряється cancellation. Дочірня задача, створена на межі перевірки, успадковує старий epoch і не виконує сканування. Успішний результат роботи, яка фактично завершилася на межі Stop, може лишитися DONE; це не дозвіл продовжувати наступну фазу. Уже зафіксований успіх не переписується заднім числом.

### Помилка до Stop

Попередня реальна помилка репозиторію лишається в результатах і журналі. Після припинення решти роботи control job може мати кінцевий стан STOPPED із повідомленням про попередні failures. Без Stop звичайна поведінка FAILED зберігається.

### Новий запуск під час Stop

Запуск відхиляється до створення стану сканування. Нині `enqueue-repo-scan.ts` викликає `startRepoScan()` до enqueue. Зміна репозиторію на IN_PROGRESS переноситься в processor після перевірки допуску; HTTP preparation не залишає IN_PROGRESS для відхиленої або вже скасованої задачі.

### Дедуплікація фаз

Ключ дедуплікації враховує покоління поряд із фазою, репозиторієм і target SHA. Старий cancelled job не блокує новий явний запуск тієї самої ревізії. У межах одного покоління зберігається дедуплікація однакової фазової роботи.

## Рестарти та legacy jobs

Jobs і persisted фази, створені до появи поля epoch, трактуються як покоління `0`. Контрольоване початкове розгортання ініціалізує глобальне покоління `0`; перший Stop закриває також legacy роботу.

При звичайному рестарті глобальний Redis epoch не скидається, незавершена операція Stop продовжується, старі queued/stalled jobs проходять guard перед скануванням, reconciliation не відновлює закриті фази, а записи RUNNING без живого processor узгоджуються через recovery та стан покоління.

Гарантія переживання рестарту передбачає збереження Redis даних. Втрата Redis сховища, ручне очищення або відкат до несумісного snapshot — окрема аварійна ситуація. Зниклий глобальний запис не можна мовчки відновити як epoch `0` на робочій системі. Приймання сканувань блокується до контрольованого відновлення бар’єра; початкова ініціалізація та аварійне відновлення мають бути описані в документації розгортання. Усі worker процеси мають використовувати новий протокол: змішане розгортання зі старим worker не підтримується.

## API-контракт

Назви нижче є рішеннями дизайну, а не твердженням про вже наявні endpoints.

### `POST /scan/stop`

Доступ: `AdminGuard`. Операція не потребує job ID або тіла запиту. Вона зупиняє всі scan jobs погодженого обсягу. Відповідь `202 Accepted` містить snapshot:

```json
{
  "epoch": 8,
  "state": "stopping",
  "stopEpoch": 8,
  "requestedAt": "2026-09-22T10:00:00.000Z",
  "finishedAt": null
}
```

Час у прикладі синтетичний. `202` підтверджує встановлення бар’єра, а не завершення workers. Недоступний Redis або неможливість підтвердити бар’єр повертає помилку сервісу; API не відповідає успіхом.

### `GET /scan/status`

Наявна admin-only відповідь зберігає `pendingCandidates` і `scannedByStatus`. Додається `runtime`:

```json
{
  "epoch": 8,
  "state": "stopping",
  "stopEpoch": 8,
  "requestedAt": "2026-09-22T10:00:00.000Z",
  "finishedAt": null,
  "queues": {
    "control": { "queued": 0, "active": 1 },
    "head": { "queued": 0, "active": 0 },
    "history": { "queued": 0, "active": 1 }
  }
}
```

`queued` рахує дозволену до сканування незавершену роботу; скасовані технічні записи не входять. `active` рахує незавершені scan processors, включно з тими, що завершують cancellation. Discovery виключається. Це кількість jobs за чергами, а не кількість одночасно сканованих репозиторіїв; їх не підсумовують під назвою «репозиторії».

Дані SQLite та Redis не є одним атомарним snapshot. UI не виводить завершення Stop із самих лічильників, а використовує підтверджений `runtime.state`.

### Start endpoints

Під час `stopping` усі шляхи запуску `scan`, `scan-repo` та `rescan-service` повертають `409 Conflict` зі стабільним кодом `scan_stopping`. Клієнт не ставить такий запит у приховану автоматичну чергу: після завершення Stop потрібна нова явна дія.

### Job status

До прикладних job statuses додаються `stopping` та `stopped`. BullMQ terminal state сам по собі не розрізняє успішний scan і штатне cancellation. Прикладний результат зупинки зберігається разом із job progress/result та однаково відображається в HTTP і WebSocket. Завершені раніше DONE/FAILED jobs зберігають свої terminal statuses, незалежно від поточного epoch.

Наявний `POST /jobs/:id/stop` лишається сумісним адресним endpoint. Глобальна кнопка UI використовує новий `POST /scan/stop`.

## UI та видимість

Адміністративний dashboard показує окремий глобальний контроль **Stop all scans**, незалежний від останнього відкритого ProgressPanel. Кнопка доступна при незавершеній scan роботі, зокрема коли root HEAD job уже DONE, а HISTORY ще виконується.

Після натискання локально показується очікування відповіді; після підтвердження API — `Stopping…`; після `runtime.state = stopped` — `Stopped`. Кнопки Start тимчасово недоступні в `stopping`, помилка API показується явно. Dashboard додає регулярне оновлення глобального стану. Reload або втрачений WebSocket не приховує Stop. Job panels підтримують нові statuses у повідомленнях, кольорах і відновленні журналу.

Показники runtime підписуються як control jobs, HEAD jobs і HISTORY jobs. Старий `Scanning`, заснований лише на `ScannedRepo.IN_PROGRESS`, не використовується як показник усієї активності. Repo DONE означає успішний HEAD у поточній моделі; UI не називає його завершенням усіх фаз, коли HISTORY ще running або cancelled.

При недоступному API не рендеряться вигадані нульові лічильники: показується недоступність стану.

## Авторизація та дані

Глобальна зупинка доступна лише адміністратору, оскільки впливає також на сканування репозиторіїв інших користувачів. Дозволи на нові сканування та RepoAuthorization не послаблюються. Epoch — серверний параметр; клієнт не задає його. Глобальний status endpoint не повертає findings, raw secrets, clone credentials або вміст файлів. Логи Stop містять лише безпечні технічні ідентифікатори, стани та лічильники.

Stop не очищує findings, не видаляє завершені jobs як побічну дію, не скидає live-test результати скасованого service rescan, не видаляє discovery candidates, Redis/SQLite дані чи volumes та не завершує весь сервер. Наявна політика cache cleanup не розширюється.

Ця область володіє persisted epoch, cancellation, умовними записами й відсутністю автоматичного відновлення.
- Web: `apps/web/src/app/dashboard.tsx`, `components/progress-panel.tsx`, API client, status types/constants та тести. Web робота можлива після узгодження API-контракту; спільні API types/contracts має одного writer.

## Критерії приймання

1. Один Stop охоплює незавершені scan jobs усіх трьох черг, включно з попередніми запусками.
2. Queued cancelled job не запускає scan worker або Git.
3. Активні HEAD, HISTORY, `scan-repo` та `rescan-service` припиняють сканування через cancellation.
4. Після Stop старий scan не бере наступний репозиторій і не запускає дозволену HISTORY.
5. Stop на межі enqueue, claim або HEAD→HISTORY не залишає роботу, що може обійти epoch.
6. Legacy jobs та pending фази без epoch зупиняються першим глобальним Stop.
7. Restart не відновлює cancelled роботу й продовжує незавершену операцію Stop.
8. Скасування не збільшує retry і не потрапляє в автоматичний requeue failures.
9. Новий Start під час зупинки відхиляється без хибного IN_PROGRESS; Start після зупинки працює.
10. Повторне явне сканування тієї самої ревізії не блокується старим cancelled job.
11. Completed результати, findings і попередні справжні failures зберігаються.
12. Звичайні errors без Stop лишаються FAILED.
13. UI показує stopping до фактичного завершення роботи; reload і background HISTORY не приховують стан.
14. Неадміністратор не може виконати глобальний Stop.
15. Недоступність Redis/API не відображається як успішна зупинка або нульова активність.

## Перевірка

Unit tests перевіряють epoch-переходи, успадкування покоління, guards, cancellation results, persisted transitions та HTTP/UI mapping. Тести гонок використовують контрольовані promises/barriers, а не випадкові затримки: enqueue одночасно зі Stop, завершення HEAD перед HISTORY, затриманий state write, новий Start під час зупинки.

Інтеграційні тести використовують ізольований Redis, окрему тестову SQLite та синтетичні репозиторії: кілька API/worker instances бачать один Stop; active/queued jobs усіх scan типів припиняються; реальний Piscina/Git шлях завершує синтетичну роботу; restart зберігає бар’єр; cancellation зберігає отримані результати без доступу до реальних leaked keys.

Full tests/builds запускає один verifier після завершення змін, послідовно для спільних ресурсів. Обов’язкові project checks: форматування змінених backend source files, API TypeScript check, API tests і build, web tests і build для UI змін, architecture review, secret-handling review і simplicity review. Невиконані або заблоковані перевірки повідомляються явно.

## Операційні обмеження

Stop є кооперативним завершенням із припиненням активного Git, а не миттєвим знищенням процесів. Синхронна ділянка обчислення, збереження отриманих результатів або очистка може затримати завершення.

При недоступному Redis workers не починають нову роботу без підтвердженого допуску. Втрата перевірки під час активного виконання запускає безпечне припинення з окремою причиною недоступності керування; вона не маскується під підтверджений користувацький Stop.

Якщо завершення неможливо підтвердити, система зберігає `stopping` і показує операційну помилку. Вона не повідомляє `stopped` лише за таймаутом. Реалізація не додає жорсткий kill усього процесу, новий scheduler або автоматичне відновлення втраченої Redis історії.

# Аналіз credsScrapper — 2026-09-21

Переглянуто API, авторизацію, чергу, виконання сканувань, збереження результатів і web UI. Код застосунку не змінено. Це огляд поточної реалізації, а не повний аудит безпеки чи навантажувальне тестування production.

## Підтверджені прогалини

### 1. P1: прогрес завдань доступний без авторизації

`GET /jobs/:id` не має guard, а `ProgressGateway` транслює події всім підключеним клієнтам. Події містять назви репозиторіїв, етапи, кількості знахідок та повідомлення про помилки. Обмеження CORS не замінює перевірку користувача. Наявна авторизація REST-ендпоінтів findings не захищає цей канал.

Джерела: `credsScrapper/apps/api/src/modules/scanner/presentation/jobs.controller.ts:14`, `credsScrapper/apps/api/src/modules/scanner/infrastructure/websocket/progress.gateway.ts:29`.

Рекомендація: зберігати власника й область доступу job; перевіряти доступ до REST-status і підписки WebSocket; надсилати події лише в авторизовані rooms. Перевірка має працювати для звичайного користувача та адміністратора.

### 2. P1: одночасні сканування одного репозиторію конфліктують

Кожен виклик `enqueueRepoScan` безумовно змінює стан репозиторію і створює новий job із тією самою текою `repo-${repoId}`. `ScanRepositoryUseCase` видаляє цю теку перед виконанням і після нього. Повторний клік, інший користувач або перетин ручного й пакетного сканування можуть знищити робочі файли активного сканування. Окремий job ID не означає окремої робочої теки.

Джерела: `credsScrapper/apps/api/src/modules/scanner/application/use-cases/enqueue-repo-scan.ts:25`, `credsScrapper/apps/api/src/modules/scanner/application/use-cases/scan-repository.use-case.ts:31`.

Відтворення з фіктивними залежностями: два паралельні запити створили два jobs з однаковим workdir.

Рекомендація: єдине захоплення репозиторію для всіх способів запуску, повернення наявного job для повторного запиту та ізоляція workdir за запуском. Окрема тека сама по собі не усуває гонок запису стану й findings.

### 3. P1: невдале сканування завершує job як успішний

`ScanRepositoryUseCase` записує `failed`, але повертає `Promise<void>` і зазвичай поглинає помилку. `BullmqJobWorker` після повернення без винятку публікує `DONE`. Для одиночного сканування це хибний успіх; підсумок пакетного сканування також не розділяє успіхи та помилки. Лічильник одиночного job залишається нульовим.

Джерела: `credsScrapper/apps/api/src/modules/scanner/application/use-cases/scan-repository.use-case.ts:56`, `credsScrapper/apps/api/src/modules/scanner/infrastructure/jobs/bullmq-job-worker.ts:100`.

Відтворення: реальний оркестратор із fake worker-result `failed` викликав `markFailed`, але job завершився без помилки з подією `done`.

Рекомендація: повертати типізований результат сканування; явно відображати його в статус job. Для пакетів рахувати succeeded/failed/skipped окремо. Тест має з'єднувати реальний оркестратор із worker, а не замінювати оркестратор fake, який кидає виняток.

### 4. P2: maxRepos порушується при кількох воркерах

Між перевіркою `reserved >= maxRepos` та `reserved += 1` є `await shouldStop()`. Кілька воркерів проходять перевірку до збільшення лічильника. Наявний тест ліміту не передає `shouldStop`, хоча BullMQ завжди його передає.

Джерело: `credsScrapper/apps/api/src/modules/scanner/application/use-cases/run-scan-loop.use-case.ts:69`.

Відтворення: `workers=4`, `maxRepos=1`, `shouldStop=async()=>false` обробили 4 фіктивні репозиторії.

Рекомендація: перевірка й резервування після асинхронної перевірки зупинки без await між ними; додати тест саме з production-комбінацією параметрів.

### 5. P2: помилки API виглядають як відсутність знахідок

`fetchPage.then(setFindingsPage).catch(() => setFindingsPage(EMPTY_PAGE))` перетворює 401, 500 та мережеві помилки на порожній список. Це порушує проєктне правило про чесний стан UI й може створити враження, що витоків немає. Ефект також не захищає від старої відповіді, яка приходить після нового запиту з іншими фільтрами.

Джерело: `credsScrapper/apps/web/src/components/findings-table.tsx:123`.

Рекомендація: окремі loading/error/empty стани, retry та скасування/ігнорування застарілих запитів. Не очищати результати як нібито успішну відповідь.

### 6. P2: панель прогресу може зависнути після втрати з'єднання

Після `connect` змінна `connected` назавжди стає `true`; обробника disconnect немає. Polling більше не запускається. Якщо job завершився під час розриву, його фінальна подія пропущена; повторне підключення не перечитує поточний стан.

Джерело: `credsScrapper/apps/web/src/components/progress-panel.tsx:70`.

Рекомендація: поновлювати polling при disconnect, перечитувати стан після reconnect, зупиняти polling після термінального стану.

### 7. Політика live-перевірок не відповідає документації

Адміністративні `AdminTestFindingUseCase` і `AdminTestRepoFindingsUseCase` свідомо не перевіряють `RepoAuthorization`. README/AGENTS описують іншу межу: live-перевірка лише за ініціативою власника після схваленої авторизації. Це не обхід AdminGuard звичайним користувачем, а суперечність між реалізованими повноваженнями адміністратора й заявленою політикою.

Джерела: `credsScrapper/apps/api/src/modules/scanner/application/use-cases/admin-test-finding.use-case.ts:16`, `credsScrapper/apps/api/src/modules/scanner/application/use-cases/admin-test-repo-findings.use-case.ts:7`.

Рекомендація: привести ці дії до явно погоджених повноважень, з перевіркою дозволу на конкретний репозиторій і аудитом. Під час огляду live-перевірки не виконувалися.

## Швидкість: замір і причини

Синтетичний локальний Git-репозиторій: 201 невеликий текстовий файл, 11 комітів, звичайний текст без credentials. Виконано реальний `RunScanJobUseCase` з `GitCliAdapter`, без Piscina, Redis, БД та мережевого clone. Вимірювання wall-clock; результат не переноситься автоматично на великі чи насичені знахідками репозиторії.

| Етап поточного проходу | Час |
|---|---:|
| Увесь виклик | 1082 мс |
| Локальний clone | 20 мс |
| Отримання історії diff | 14 мс |
| 201 окремий git show для HEAD | 919 мс |
| scanText: 412 викликів, приблизно 1,60 МБ | 113 мс |

Окреме порівняння читання тих самих 201 файлів, три повтори:

| Варіант | Час повторів | Медіана |
|---|---|---:|
| Окремий git show на файл | 892 / 890 / 975 мс | 892 мс |
| Один git cat-file --batch | 12 / 16 / 13 мс | 13 мс |

Вміст перевірений SHA-256: байти однакові. Приблизно 67× стосується лише читання HEAD у цьому експерименті, не всього сканування. Batch-прототип буферизував маленький тестовий результат; production-реалізація має обробляти потік із контрольованим обсягом даних у пам'яті.

Інші причини повільної роботи, видимі в коді:

- `git log -p` завантажує всю історію одним рядком до 512 МБ, потім створює масив сегментів. До завершення читання аналіз історії не починається.
- Усі патерни проходять кожен текст окремо. Після обчислення entropy кандидат знову перевіряється через `matchedSpans.some(...)`. Для T кандидатів і P pattern-spans це до O(T×P) перевірок.
- Findings передаються між потоками по одному, накопичуються всі разом і лише після сканування дедуплікуються та записуються.
- Piscina розпаралелює репозиторії; один репозиторій є одним завданням. Більше workers не розпаралелює його внутрішній прохід.
- Progress-log росте без межі; кожен updateProgress записує весь накопичений масив. Сумарний обсяг серіалізації росте квадратично від кількості подій. Retention для завершених BullMQ jobs не налаштований.

## Запропонований алгоритм

### Перший етап: зберегти поведінку та прибрати зайві витрати

1. Читати HEAD через один довгоживучий `git cat-file --batch`, із прив'язкою object ID до шляхів, обробкою binary та лімітів розміру. Batch-протокол читати за розміром об'єкта, не розбивати довільний вміст на рядки.
2. Історію diff читати поступово через spawn та AsyncIterable, із коректною обробкою меж записів. Зберегти наявну область refs і правила пропуску шляхів.
3. Передавати й записувати findings пакетами з backpressure, дедуплікувати повтори раніше. Фінальний ack повинен гарантувати, що всі результати прийняті й записані.
4. В engine відсортувати/об'єднати matched intervals і перевіряти перекриття проходом із двома вказівниками або двійковим пошуком. Дешеві перевірки кандидатів робити до entropy, а пропуск уже розпізнаних ділянок — до дорогих обчислень. Зберегти поведінку для багаторядкових ключів.
5. Додати вимірювання стадій: clone, Git read, detection, transfer, DB write. Показувати поточну стадію та байти/файли, а не тільки кількість завершених репозиторіїв.

### Другий етап: аналіз унікальних Git blob із кешем

`Обрані refs → версії файлів → унікальні blob ID → batch reader → detector → кеш → прив'язка до path/commit → БД`.

Blob — об'єкт із вмістом конкретної версії файлу. Однаковий object ID не потрібно повторно аналізувати для кожної появи в історії чи HEAD. Кешувати результат за `(blob ID, версія detector/config)`, включно з результатом «знахідок немає». Зберігати mapping до всіх потрібних шляхів і комітів окремо; не втрачати історію появи знахідок. Path-exclusions застосовувати до кожної прив'язки: той самий blob може бути у дозволеному й виключеному шляху.

Для наступних проходів репозиторію аналізувати нові blob, а не повторювати всю історію. Зміна правил інвалідує кеш; force-push та зміна refs потребують перевірки досяжності, а не сліпого діапазону old..new. Не розширювати охоплення на всі refs без окремого рішення.

Важливий компроміс: у великому файлі з частими маленькими правками кожна версія має новий blob ID. Сканування повних версій може читати більше байтів, ніж аналіз diff. Тому blob-підхід варто порівняти з потоковим diff-підходом на репрезентативних, дозволених репозиторіях. Зміна способу читання також потребує тестів семантики `leakCommits`, перейменувань, merge-комітів, видалених файлів і багаторядкових секретів.

Нативна пакетна обробка описана в [git-cat-file](https://git-scm.com/docs/git-cat-file), обхід досяжних об'єктів — у [git-rev-list](https://git-scm.com/docs/git-rev-list). `rev-list --objects` сам по собі не замінює повний mapping blob → усі path/commit.

## Подальші поліпшення

- Валідувати DTO під час виконання: типи, цілі числа, діапазони workers/maxRepos/limit/offset. TypeScript-клас без runtime validation не захищає HTTP-вхід.
- Додати індекси за фактичними запитами: findings(repoId), queue status/order, authorizations(userId, status). Перевіряти план SQL і cardinality, а не додавати індекси навмання. У schema.prisma цих індексів зараз немає.
- Обмежити log retention і зберігання завершених jobs; прибрати необмежені масиви зі шляху прогресу.
- Не збільшувати кількість портів без потреби: основні межі вже виділені. Конкретні відступи — process.env у application/enqueue-repo-scan та прямі звернення controller → queue port замість заявлених use-cases. Вони менш термінові за correctness і доступ.
- Визначити строк життя сесій і відкликання JWT: guard довіряє ролі в токені до завершення його строку. Зберігання токена в localStorage підсилює наслідки можливого XSS, але саме XSS у цьому огляді не доведено.
- Plaintext findings у БД — уже задокументоване рішення MVP, не нова знайдена помилка. Відкладати його перегляд на окреме рішення щодо зберігання й доступу.

## Перевірки

- API unit: 45 suites, 312 тестів — пройшли.
- Web: 13 файлів, 55 тестів — пройшли.
- Чотири локальні відтворення: гонка maxRepos, failed→done, повторні jobs зі спільним workdir, відсутність guard у GET job — підтверджені.
- Мікробенчмарк Git reader: три повтори, вміст batch і sequential звірено.
- Redis/DB integration та production builds не запускалися. Наявні Redis-тести використовують спільне ім'я черги; їх потрібно ізолювати перед запуском поруч із живим застосунком.
- Живі репозиторії, БД знахідок і реальні credentials не використовувалися. Зміни попередньої міграції залишені як були.

# credsScrapper: результати профілювання та вердикт

**Вердикт: зараз вигідніше оптимізувати Node-детектор і розділити швидкий скан HEAD та фонову історію. Переписування всього сервісу на Go не обґрунтоване вимірюваннями.**

Експерименти збережено в `credsScrapper/scripts/performance-lab/`. Вони не перемикають production-сканер на новий алгоритм. Жоден знайдений credential не використовувався для live-перевірки.

## Що виміряно

- 16 спроб скану з локального кешу: 4 репозиторії × 4 варіанти; ліміт 40 секунд. Великі історії, що не завершилися, явно позначені timeout.
- 54 контрольні скани: 3 репозиторії × 6 варіантів × 3 повтори, останні 100 комітів плюс весь HEAD. Порядок варіантів ротується всередині серії.
- Додатковий подвійний прогін трьох контрольних сканів: кожен текст перевірено і базовим, і fast-node детектором; повні об’єкти знахідок збігаються.
- 6 мережевих отримань одного SHA: full Git, shallow Git, 3 архіви, GitHub tree + 30 blobs. Окремо звірено всі 30 шляхів та байти архіву з Git HEAD.
- Go/Node: лише ядро ентропії, 4 синтетичні набори, warm-up + 3 виміри кожного варіанта. Збігаються кількість, порядок і позиції/довжини токенів.
- 6 записів синтетичних наборів у окремі тимчасові SQLite: production-БД не використовувалася.

## Результати контрольних сканів

Медіана трьох прогонів, секунди. Покриття однакове: **100 останніх комітів + HEAD**, а не вся історія.

| Репозиторій | Node зараз | Масив лічильників | Маркери перед regex | Обидві оптимізації | Прискорення |
|---|---:|---:|---:|---:|---:|
| EduMarttiins/lousa-de-estudos | 0.285 | 0.253 | 0.310 | 0.231 | 1.23× |
| bi-cabana/cabana-dashboards | 24.651 | 20.056 | 14.302 | 11.237 | 2.19× |
| deviyl/kfc | 2.691 | 2.761 | 2.659 | 2.555 | 1.05× |

Невеликі різниці на коротких прогонах можуть бути шумом: min–max збережені у JSON і показані на графіку. Дві серії (базові варіанти та prefilter/fast-node) виконані послідовно, не одним повністю рандомізованим експериментом.

Після перенесення fast-node у production-код виконано ще три прогони тієї
самої вибірки. Медіани зібраного застосунку: `lousa-de-estudos` — 0.317 с,
`cabana-dashboards` — 10.923 с, `kfc` — 2.393 с. Для важкого детектором
репозиторію це 2.26× проти початкової production-медіани 24.651 с.

### Де затримка

| Репозиторій | Комітів загалом | Git-об’єкти | Що побачили |
|---|---:|---:|---|
| EduMarttiins/lousa-de-estudos | 1 033 | 2.64 MiB | Повний базовий скан з кешу завершився за 0.82 с |
| bi-cabana/cabana-dashboards | 2 082 | 341.51 MiB | За ~40 с: 296 МБ тексту, понад 2 млн подій; 86% часу — детектор; історія не завершена |
| deviyl/kfc | 27 689 | 320.01 MiB | За ~40 с близько 90% часу — ітерація Git history; історія не завершена |
| a1pro/documentation | 5 106 | 802.12 MiB | За ~40 с близько 75% часу — детектор; історія не завершена |

Додатково в наявних робочих каталогах є Git-об’єкти на 7 GiB і 21 GiB. Це спостереження про розмір кешу, не вимірювання цих двох повних сканів.

Діагностичний прогін cabana (1 останній коміт + HEAD, з накладними витратами інструментації): ~3.46 с детекції, з них Terraform regex ~1.29 с, ентропія ~0.88 с, AWS secret regex ~0.21 с. Перевірка обов’язкового `.atlasv1.` пропускає дорогий Terraform regex там, де збіг неможливий. Аналогічні безпечні маркери використані для Mailchimp та AWS.

### Відхилені варіанти

- Вимкнення rename detection: на повній історії маленького репозиторію кількість подій змінилася з 7 720 до 9 590. Це не прозора оптимізація з тотожними результатами, навіть якщо на останніх 100 комітах результати збіглися.
- Кеш 32 MiB за точним текстом diff: майже немає влучань; коміти змінюють текст, а хешування/збереження додає витрати. На kfc медіана навіть зросла.

## Git чи API

Один публічний репозиторій, той самий SHA. **Full Git включає історію; решта — тільки HEAD.**

| Спосіб | Спостережуваний час | Покриття |
|---|---:|---|
| Full bare clone | 27.62 с | HEAD + історія |
| Shallow clone | 2.17 с | HEAD |
| GitHub archive (медіана 3) | 1.52 с | HEAD |
| GitHub tree + blobs, 31 запит, concurrency=4 | 4.84 с | HEAD |

Архів і API містили 30 файлів, 31 619 536 байт нестисненого вмісту. Архів ~12 MB, shallow Git ~5.6 MB на диску, full Git ~358 MB. CDN/мережевий кеш не очищався; full/shallow/API мають лише по одному мережевому виміру. Архів не шукає секрети, видалені з HEAD. GitHub API для всієї історії тут не реалізовано й не виміряно — не можна приписувати йому час snapshot API.

### Реалізований шлях

Production-сканер тепер розділяє роботу на дві незалежні фази. HEAD отримує
shallow Git snapshot і відразу зберігає актуальні знахідки; повна історія
працює у фоновій черзі з окремим кешем та одним воркером. На наведеному вище
мережевому вимірі це скорочує доступність HEAD з 27.62 с до 2.17 с, тобто
приблизно у **12.7×**, без хибної заяви, що історію вже перевірено. Це
порівняння саме часу отримання Git-даних одного SHA; повний end-to-end час
залежатиме від розміру HEAD, кількості збігів і швидкості диска.

## Go проти Node

Мілісекунди, медіана 3; лише ентропія, без файлового вводу/IPC/запуску процесу.

| Синтетичний набір | Node поточний | Node typed array | Go regexp | Go byte loop |
|---|---:|---:|---:|---:|
| clean | 47.46 | 26.76 | 115.49 | 1.01 |
| dense | 55.05 | 34.81 | 233.98 | 24.89 |
| longline | 17.63 | 4.95 | 63.86 | 1.78 |
| edges | 8.95 | 3.92 | 40.93 | 3.00 |

Go byte loop швидкий, але прямий перенос у Go regexp виявився повільнішим за Node на цих наборах. Це не бенчмарк повного Go-сканера: решта regex, placeholder-фільтри, контекст, Unicode-позиції та історія не портовані. У діагностичному прогоні ентропія становить приблизно чверть часу детекції; її прискорення не дасть такого самого множника всьому скану.

## Запис результатів

- 10,000 синтетичних подій → 10,000 унікальних знахідок: медіана 328 мс у тимчасовій SQLite.
- 100,000 синтетичних подій → 1,000 унікальних знахідок: медіана 139 мс у тимчасовій SQLite.

Це write-only тест. Він не вимірює production-БД, конкурентні записи або передачу мільйонів подій через Piscina. До оптимізації всі події накопичувалися в `collectedFindings` перед дедуплікацією. Просте відкидання повторів було б некоректним: треба зберегти commit sightings і пріоритет шляху з HEAD.

Після профілювання production worker почав агрегувати однаковий секрет до
передачі через Piscina. Контрольний integration fixture із 600 повторів у
commit diff та 600 повторів у HEAD тепер передає **1 finding event замість
1 200**. Подія містить усі унікальні commit SHA, а шлях із HEAD має пріоритет
над службовим `<commit-diff>`. Persistence integration test підтверджує, що
компактний запис відновлює повний `leakCommits`.

## Практичний наступний крок

1. ✅ Fast-node варіант перенесено в production-детектор; corpus і граничні entropy-тести пройшли.
2. ✅ Окремі режими реалізовано: швидкий **HEAD** через shallow Git/cache та фоновий **історичний** скан через Git; UI показує їхнє покриття окремо.
3. ✅ Історія має окремий checkpoint, чергу та воркер; прогрес містить коміти/байти, а часовий і дисковий ліміти повертають `incomplete`.
4. ✅ Worker передає компактні агрегати з commit sightings; еквівалентність persistence merge покрита integration-тестами.
5. Go розглядати для окремого детектора лише після вимірювання повного прототипу з усіма правилами й вартістю IPC. NestJS API та UI не є доведеним вузьким місцем.

## Межі й відтворюваність

Локальні профілі виключають clone/fetch, cache lock, Piscina, Redis і production-персистенцію; HMAC callback додає витрати. ОС page cache не очищався. Ранні пошукові прогони могли перетинатися з іншими діагностичними процесами; контрольні серії та фінальні kernel/DB тести виконані послідовно. Timeout означає незавершений скан, а не прогноз його повного часу. Усі цифри — для цієї машини та зафіксованих SHA.

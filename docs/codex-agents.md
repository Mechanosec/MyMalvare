# Агенти Codex у MyMalvare

Проєкт використовує штатні ролі Codex, без додаткового плагіна.
Правила запуску — у кореневому `AGENTS.md`, конфігурація — у
`.codex/config.toml`, інструкції ролей — у `.codex/agents/*.toml`.

| Роль | Відповідальність | Що може змінювати |
| --- | --- | --- |
| `api_worker` | NestJS, use-cases, ports/adapters, API-тести | Лише призначені файли API |
| `web_worker` | Next.js, UI, доступність, стани запитів | Лише призначені файли UI |
| `verifier` | Відтворення, незалежна перевірка, tests/build | Тести лише за окремим призначенням; звичайні артефакти перевірки |
| `reviewer` | Коректність, секрети, архітектура, простота | Нічого; профіль read-only |

Головний агент координує роботу й інтегрує результат. Зазвичай достатньо
одного або двох допоміжних агентів; конфіг обмежує одночасних дітей трьома.
Чотири визначені ролі не означають чотири одночасні запуски. Рев’ю можна
запустити після завершення worker, звільнивши його слот.

## Як просити

- «Реалізуй фічу. API і UI віддай окремим агентам після узгодження контракту,
  потім незалежно перевір тести й зроби рев’ю».
- «Попроси reviewer перевірити поточний diff без правок».
- «Нехай verifier відтворить баг на синтетичних даних, поки ти аналізуєш код».

Завдяки `AGENTS.md` для доречних незалежних підзадач не потрібно щоразу
просити делегування. Для маленьких правок головний агент працює сам.
Додаткові агенти споживають ресурси сесії; створювати їх без конкретної
паралельної роботи немає сенсу.

## Правила передачі роботи

Перед запуском головний агент задає:

1. Конкретний результат і критерії приймання.
2. Точні файли, які дозволено редагувати, або режим read-only.
3. Узгоджені API-контракти й залежності від інших задач.
4. Потрібні перевірки та право запускати їх у спільному середовищі.

Результат агента: зміни, файли, фактичні команди й результати перевірок,
невирішені питання. Один файл одночасно редагує один агент. Повні збірки,
тести зі спільною БД і керування браузером мають одного виконавця.
Справжні ключі не передаються агентам і не використовуються для тестування.
Дозвіл налаштувати агентів не є дозволом публікувати код.

## Сумісність і запуск

Ролі явно зареєстровані через `agents.<role>.config_file` для сумісності
з локальним Codex CLI 0.130. Файли також містять `name`, `description` і
`developer_instructions` для клієнтів із автоматичним пошуком агентів.
`max_threads` — сумісна назва ліміту; новіша документація також описує
`max_concurrent_threads_per_session`.

Модель, reasoning effort і політика дозволів успадковуються від сесії;
конфіг не фіксує тариф чи конкретну модель. Reviewer запитує read-only
режим. Поточні runtime-налаштування клієнта можуть мати вищий пріоритет,
тому інструкція не редагувати файли також записана в його профілі.

Після зміни конфігурації почни нову сесію в цьому репозиторії. Проєктні
конфіги залежать від довіри до проєкту та можливостей клієнта; чинна сесія
може не перечитати ролі автоматично. Якщо доступний лише generic spawn,
головний агент передає прочитані інструкції ролі явно.

Під час налаштування 2026-09-21 локальний CLI 0.130 не приймав значення
`service_tier = "default"` у глобальному конфігу користувача. Проєктний
setup його не змінює. Читання ролей перевірено через локальний `config/read`
із тимчасовим override `-c 'service_tier="fast"'`, без запуску моделі.
Це не встановлює fast tier для проєкту. Якщо запускаєш саме цей CLI без
override, спершу узгодь версію CLI та глобальний конфіг.

## Перевірка налаштувань

Для правок лише цих документів/конфігів достатньо TOML-парсингу, перевірки
шляхів `config_file`, `git diff --check` та перевірки читання конфіга клієнтом.
Запускати API/UI test suites через зміну інструкцій не потрібно.
Не перевіряй setup запуском реального сканування чи live key testing.

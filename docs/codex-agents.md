# Агенти Codex у MyMalvare

Проєкт використовує штатні ролі Codex, без додаткового плагіна.
Правила запуску — у кореневому `AGENTS.md`, конфігурація — у
`.codex/config.toml`, інструкції ролей — у `.codex/agents/*.toml`.

| Роль | Відповідальність | Що може змінювати |
| --- | --- | --- |
| `planner` | Брейншторм, дизайн, декомпозиція, письмові плани | Нічого; профіль read-only |
| `api_worker` | NestJS, use-cases, ports/adapters, API-тести | Лише призначені файли API |
| `web_worker` | Next.js, UI, доступність, стани запитів | Лише призначені файли UI |
| `verifier` | Відтворення, незалежна перевірка, tests/build | Тести лише за окремим призначенням; звичайні артефакти перевірки |
| `reviewer` | Коректність, секрети, архітектура, простота | Нічого; профіль read-only |

Головний агент координує роботу й інтегрує результат. Зазвичай достатньо
одного або двох допоміжних агентів; конфіг обмежує одночасних дітей трьома.
П’ять визначених ролей не означають п’ять одночасних запусків. Рев’ю можна
запустити після завершення worker, звільнивши його слот.

Для змістовних планів `planner` використовує `gpt-6-astra` / `medium`.
`api_worker` використовує `gpt-6-sol` / `high` для складних змін сканера,
авторизації та конкурентності; `web_worker` — Sol/`medium`. Основна сесія
має Sol/`medium`, `verifier` — `medium`, `reviewer` — Sol/`high`. Явний вибір
моделі в клієнті може перевизначити основну сесію.

Коли потрібні архітектура, міжкомпонентний дизайн, складне порівняння
варіантів або письмовий план за вимогою користувача чи навички, головний
агент передає цю роботу `planner`. Для інтерактивного брейншторму він
пересилає лише рішення й потрібні обмеження. Якщо потрібен файл
специфікації, Astra готує зміст, а головний агент записує його до
репозиторію. Уже погоджені й обмежені задачі не потребують нового
планувального handoff. Обов’язкові етапи навичок лишаються чинними.

Навички Codex не перемикають модель самі: правило працює через делегування
ролі. Якщо доступний тільки generic spawn, головний агент читає профіль
ролі й передає його інструкції, модель і reasoning effort. Короткий або
порожній fork історії отримує лише потрібний контекст задачі, правила
проєкту й поточний етап навички. Якщо агента або модель не вдається
запустити, головний агент повідомляє про обмеження.

## Як просити

- «Реалізуй фічу. API і UI віддай окремим агентам після узгодження контракту,
  потім незалежно перевір тести й зроби рев’ю».
- «Попроси reviewer перевірити поточний diff без правок».
- «Нехай verifier відтворить баг на синтетичних даних, поки ти аналізуєш код».

Завдяки `AGENTS.md` для доречних незалежних підзадач не потрібно щоразу
просити делегування. Для маленьких правок без планувальної фази головний
агент працює сам.
Додаткові агенти споживають час і токени; створювати їх без конкретної
паралельної роботи немає сенсу. Одного рішення користувача для поточного
етапу достатньо — нове погодження потрібне лише за зміни обсягу або за
обов’язковою вимогою навички.

## Як проходить задача

Головний агент формулює результат і критерії приймання. Якщо потрібне
змістовне планування, він передає його `planner` на Astra/medium і проходить
обов’язкові етапи погодження. Після цього веде роботу до завершення:

1. Розподіляє лише незалежні зміни між workers; для кожного визначає
   файли, залежності, контракт і цільові перевірки. Тісно пов’язані або
   дрібні зміни виконує сам. UI може стартувати після стабілізації API-
   контракту, не чекаючи готового endpoint.
2. Під час редагування запускає цільові тести. Високоризикові інтеграційні
   сценарії перевіряє до фінальних повних прогонів. Спільні збірки, БД і
   браузер не використовуються паралельно кількома агентами.
3. Для суттєвих або чутливих до безпеки змін робить одне інтегроване рев’ю
   наприкінці, застосувавши всі обов’язкові checklists. Раннє рев’ю потрібне
   лише за конкретного ризику, який не може чекати.
4. Передає згруповані зауваження відповідальному виконавцю, інтегрує
   виправлення, а потім дає одному `verifier` повні тести й збірки. Успішні
   повні перевірки повторює лише після релевантних нових правок.
5. Звітує про поведінку, фактичні результати перевірок і невирішені ризики.
   Завершене доручення агента саме собою не означає готовність усієї задачі.

Поки агенти працюють, головний агент виконує незалежну роботу або чекає
змістовної події, не опитуючи їх що 30 секунд; користувач отримує оновлення
не рідше ніж раз на 60 секунд під час тривалої роботи.

Проміжні передачі роботи не потребують окремого підтвердження. Головний агент
звертається до користувача, коли бракує суттєвих даних, змінився обсяг або
потрібне зовнішнє рішення. Необхідні погодження навичок зберігаються.
Поточний етап і наступна дія лишаються в контексті задачі, щоб після
переривання можна було продовжити без окремого файлу стану. Коміт, пуш і
деплой залишаються окремими діями за правилами `AGENTS.md`.

## Правила передачі роботи

Перед запуском головний агент задає:

1. Конкретний результат і критерії приймання.
2. Точні файли, які дозволено редагувати, або режим read-only.
3. Узгоджені API-контракти й залежності від інших задач.
4. Потрібні перевірки та право запускати їх у спільному середовищі.

Результат агента: зміни, файли, фактичні команди й результати перевірок,
невирішені питання. Один файл одночасно редагує один агент. Повні збірки,
тести зі спільною БД і керування браузером мають одного виконавця.
Справжні ключі не передаються агентам і не використовуються для тестування.
Дозвіл налаштувати агентів не є дозволом публікувати код.

## Сумісність і запуск

Ролі явно зареєстровані через `agents.<role>.config_file` для сумісності
з локальним Codex CLI 0.130. Файли також містять `name`, `description` і
`developer_instructions` для клієнтів із автоматичним пошуком агентів.
`max_threads` — сумісна назва ліміту; новіша документація також описує
`max_concurrent_threads_per_session`.

Політика дозволів успадковується від сесії; конфіг фіксує модель для
основної сесії, planner, workers та reviewer і effort для verifier.
Reviewer запитує read-only режим. Поточні runtime-налаштування клієнта
можуть мати вищий пріоритет, тому інструкція не редагувати файли також
записана в його профілі.

Після зміни конфігурації почни нову сесію в цьому репозиторії. Проєктні
конфіги залежать від довіри до проєкту та можливостей клієнта; чинна сесія
може не перечитати ролі автоматично. Якщо доступний лише generic spawn,
головний агент передає прочитані інструкції ролі явно.

Під час налаштування 2026-09-21 локальний CLI 0.130 не приймав значення
`service_tier = "default"` у глобальному конфігу користувача. Проєктний
setup його не змінює. Читання ролей перевірено через локальний `config/read`
із тимчасовим override `-c 'service_tier="fast"'`, без запуску моделі.
Це не встановлює fast tier для проєкту. Якщо запускаєш саме цей CLI без
override, спершу узгодь версію CLI та глобальний конфіг.

## Перевірка налаштувань

Для правок лише цих документів/конфігів достатньо TOML-парсингу, перевірки
шляхів `config_file`, `git diff --check` та перевірки читання конфіга клієнтом.
Запускати API/UI test suites через зміну інструкцій не потрібно.
Не перевіряй setup запуском реального сканування чи live key testing.

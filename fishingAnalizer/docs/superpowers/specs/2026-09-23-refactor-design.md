# Рефакторинг Fishing Analizer

Дата: 2026-09-23. Напрям модульного рефакторингу погоджено; ця специфікація очікує перегляду користувачем.

## Мета

Зробити TypeScript-код зрозумілим за назвами модулів, їхніми залежностями й послідовністю обробки відкритого листа. Зберегти можливості, команди запуску, HTTP API, каталоги `backend`, `extection`, `localModel` та поведінку в Gmail. Нові функції й фреймворки не входять у роботу.

## Поточні проблеми

- Production-код змішує TypeScript imports, CommonJS і browser globals. `require()` послаблює перевірку типів.
- `controller.scan()` одночасно читає налаштування, керує згодою, кешем, IPC і DOM; стан панелі визначає за українським текстом.
- `backend/index.ts` містить запуск сервера, маршрути, валідацію, помилки й HTML.
- Адреса сервера, режими, статуси й правила адреси повторюються. Build script і тести не входять у перевірку TypeScript.

## Модулі й відповідальності

Стандартні TypeScript `import`/`export` використовуються в усіх вихідних модулях. esbuild створює самодостатні Chrome bundles і CommonJS-артефакт бекенду. Проєкт не переходить на Node ESM. Не додаються DI-контейнер, базові класи адаптерів, registry провайдерів або загальний framework станів.

### Спільні модулі

`types.ts` переноситься в `shared/contracts.ts`: `MailMessage`, `Mode`, `Status`, `Observation`, `AnalyzeResult`, типи запиту й помилки, невеликі перевірки недовірених JSON/IPC-значень. Зовнішні значення мають тип `unknown` до перевірки. Перенесення перевірок не змінює чинний контракт і не додає нових обов’язкових полів до раніше допустимих запитів.

Новий `shared/settings.ts` містить адресу бекенду й режим за замовчуванням, тип налаштувань, перевірку loopback-адреси, побудову endpoint аналізу та ключа згоди. Формат storage і ключа `${serverUrl}|${mode}` залишається сумісним. Спільні модулі не імпортують Node або Chrome API.

### Розширення

| Модуль | Відповідальність |
|---|---|
| `extection/dom.ts` | Вибір розгорнутих повідомлень і читання дозволених видимих полів Gmail. |
| Новий `extection/panel.ts` | Створення панелі й показ згоди, очікування, результату або помилки. |
| `extection/controller.ts` | Сканування, ідентичність листів, кеш, запити та актуальність відповідей. |
| `extection/content.ts` | MutationObserver, навігація й реакція на зміну налаштувань. |
| `extection/background.ts` | Перевірка IPC, джерела, режиму й згоди; запит до бекенду та перевірка відповіді. |
| `extection/options.ts` | Читання й збереження налаштувань та відкликання згоди. |

Панель має явний стан `consent / pending / success / error`. Текст інтерфейсу не визначає стан. Renderer не має доступу до storage або network.

Кеш контролера використовує discriminated union `pending / success / error`. Ключ містить адресу й режим, ідентифікатор повідомлення та хеш видимих даних; повний текст листа в кеші не зберігається. `scan()` поділяється на іменовані кроки: читання контексту; пошук актуальних листів; створення ідентичності; показ згоди чи кешу або запуск запиту; повторна перевірка перед показом відповіді. Зберігаються перевірки generation, маршруту, DOM-вузла, ключа панелі, налаштувань, згоди, розгорнутого стану й хешу листа. DOM-селектори й ліміти отримують назви; повторне читання тексту прибирається без зміни значення `truncated`.

### Бекенд

| Модуль | Відповідальність |
|---|---|
| `backend/index.ts` | Лише запуск сервера на поточній адресі й порту. |
| Новий `backend/http.ts` | `createHandler`, маршрути, CORS, JSON, статуси HTTP і безпечні помилки. |
| Новий `backend/home-page.ts` | Поточна статична HTML-сторінка. |
| `backend/analyze.ts` | Спостережувані ознаки, рішення моделі, остаточний статус і обмеження. |
| `backend/adapters.ts` | Конфігурація Jev/Laya, Decisions API, перевірка відповіді. |

`analyze.ts` отримує іменовані функції збирання ознак, визначення статусу та формування обмежень без зміни пріоритетів правил. Невідповідність видимого й фактичного доменів означає `suspicious`; інші ознаки чи скорочений лист не дозволяють `no_signals`. У `adapters.ts` конфігурація двох провайдерів відділяється від спільного HTTP-виклику без класів і registry. Зберігаються `state.message`, `questions`, моделі, endpoints, таймаути й заборона redirects. HTTP-обробник передає аналізатору лише дозволені поля.

## Потік даних

```text
Gmail DOM → dom → controller (згода, ідентичність, кеш)
→ background (IPC, HTTP) → backend/http (валідація, проєкція)
→ analyze (ознаки + модель) → adapters (Jev або Laya)
→ controller (повторна перевірка актуальності) → panel
```

Chrome storage і надалі зберігає налаштування та згоду. Вміст листа використовується лише для поточного аналізу.

## Сумісність і безпека

Зберігаються `GET /`, `GET /health`, `POST /analyze`, preflight, HTTP-статуси, формат запитів і відповідей, режими `jev / local`, три стани оцінки, npm-команди, `dist/extection`, Chrome permissions і CORS. Згода потрібна до першого запиту й окремо для іншого serverUrl/mode. Однакові дані листа в чинному контексті не створюють повторного запиту; відповідь іншого або вже зміненого листа не показується.

Зберігаються фіксований OpenRouter endpoint, loopback-обмеження, таймаути, заборона redirects, серверне зберігання ключа, ліміти вхідних даних і проєкція дозволених полів. Текст листа не записується й не логується. Недовірений текст показується через `textContent`, HTML листа не вставляється, посилання не відкриваються. Недоступний аналіз дає помилку без вердикту.

## Збірка й міграція

esbuild збирає `content.ts`, `background.ts`, `options.ts`. Manifest завантажує один `content.js` із залежностями DOM reader та контролера. Умовні UMD-експорти й `FishingDom`/`FishingController` видаляються. Тести імпортують актуальні модулі через збірку; імпорт HTTP-обробника не запускає сервер. TypeScript перевіряє production-код, build script і тести. Тестові doubles описують лише використані частини Chrome API.

Послідовність: зафіксувати базові тести; погодити спільні типи; перевести модулі й збірку на imports/exports; відокремити HTTP/HTML; відокремити panel renderer і спростити контролер; додати ризикові перевірки; оновити README; провести review та фінальні перевірки. Parent володіє `shared/*`, build script, tsconfig, manifest і README. Після узгодження контрактів backend і extension можна змінювати незалежно з одним власником на файл. Один verifier запускає повні тести й збірку після інтеграції.

## Критерії прийняття

1. Усі 19 наявних поведінкових тестів проходять без зміни очікувань.
2. Production-модулі використовують imports/exports без browser globals для зв’язування модулів.
3. Панель не визначає стан за текстом; `backend/index.ts` лише запускає сервер.
4. Спільні контракти й налаштування використовуються компонентами; TypeScript перевіряє код, збірку й тести.
5. `npm run build` та `npm test` успішні; README пояснює модулі й запуск.
6. Додані тести запізнілої відповіді після відкликання згоди чи зміни адреси, network/invalid response/retry, DOM-мутацій від панелі, виконання зібраного `content.js`, дозволених полів/CORS/endpoints/помилок провайдерів.

Використовуються синтетичні листи й відповіді. Реальних платних викликів немає. Якщо перевірка в Chrome/Gmail не виконувалась, це явно зазначається у звіті.

## Ризики й межі

Головний ризик — втратити асинхронні перевірки актуальності. Другий — Node-тести можуть не виявити поломку Chrome bundle. Третій — перенесення runtime-перевірок може випадково змінити контракт. Усі три ризики мають окремі тести.

Не входять: нові можливості, редизайн/popup, нові селектори Gmail, зміна моделей/промптів/правил, перевстановлення Laya, нові runtime-залежності, Gmail API, історія листів, commit/push/deploy.
